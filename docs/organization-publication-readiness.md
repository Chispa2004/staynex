## Correcciones de esta pasada

- `OrganizationDirectoryClient`, `AppShell`, `HotelWorkspaceSwitcher` y `UserManagementClient` usan `useDashboardLanguage().tx` para los textos solicitados. El selector también traduce sus etiquetas accesibles. `translations.js` contiene «Usuarios», «Accesos a hoteles», la explicación y los roles. Se mantienen identificadores, permisos, fórmulas y distribución; solo se añade estilo para la explicación.
- `updateTicketStatus` comprobaba el ticket por hotel pero continuaba con la actualización al no encontrarlo, devolviendo 500. Ahora termina con 404 antes de escribir; el handler conserva ese estado. El HTTP del build reproduce y protege esta regresión.
- `/api/settings/users` devolvía 500 al carecer de contexto autorizado. Ahora responde 401 para sesión ausente/inválida y 403 para acceso denegado. Las consultas y guardas de escritura se conservan.
- El preflight de organizaciones amplía la inspección de columnas, restricciones, triggers, funciones/ACL, privilegios efectivos, RLS, Realtime y conflictos de identidad. Usa transacción READ ONLY y `row_security=off`: una inspección insuficientemente privilegiada falla, en lugar de informar ceros filtrados.

## Procedimiento de publicación futura

Este procedimiento no es autorización para ejecutarlo. No se exige incorporar hoteles existentes para publicar. Mantener los flags actuales y `SEND_AUTOMATIONS=false` en todas las fases.

1. **Confirmar destino y catálogo.** Registrar repositorio, SHA aprobado, proyecto Supabase efectivo y versiones desplegadas; obtener respaldo privado verificable de esquema, asignaciones, identidades y auditoría. Ejecutar `supabase/sql/preflight_organizations.sql` con inspector que pueda ver el catálogo completo, guardar salida fuera de Git y revisar cada resultado. La consulta hace `BEGIN READ ONLY` y `ROLLBACK`; no corrige nada. Comprobar PostgreSQL >=15, roles Auth/Supabase y `auth.users`/`auth.uid()`/`auth.jwt()` disponibles.
2. **Resolver dependencias, sin reaplicar SQL histórico a ciegas.** Deben existir los contratos versionados de `create_hotels_and_hotel_users.sql`, `create_user_roles_and_hotel_assignments.sql`, `add_platform_role_to_hotel_users.sql`, `create_platform_audit_logs.sql`, `create_enterprise_audit_logs.sql` y `rls_phase_2_write_protection.sql`. Contrastar tipos/defaults/restricciones e índices con el SQL de organizaciones. `hotels` necesita UUID `id`, nombre, slug, ciudad, país, zona horaria y `metadata`; `hotel_users` necesita UUID de hotel/usuario/fila, correo, rol, estado, rol interno, default y marcas temporales usadas por el contrato. Auditorías deben aceptar los campos insertados por las funciones y `writeEnterpriseAuditLog`. Verificar `staynex_can_read_hotel(uuid)` y `staynex_can_write_hotel(uuid,text[])`, su propietario/search_path/ACL y tablas cubiertas por RLS. Si falta una dependencia o hay definición incompatible, detenerse y preparar el ajuste concreto por separado. El preflight enumera evidencias, no certifica automáticamente compatibilidad.
3. **Identidades e índices.** Cero asignaciones activas con `user_id IS NULL` antes del esquema: la migración aborta si existen. Cuentas verificadas deben corresponder al UUID existente; no inferir por marca/correo. Resolver privadamente emails ausentes y colisiones normalizadas antes de incorporar cada hotel. Revisar índices únicos adicionales, restricciones con otro nombre y objetos de organizaciones preexistentes; `IF NOT EXISTS` no valida su compatibilidad. No sobrescribir ni borrar objetos/datos para forzar PASS.
4. **Pausar y drenar escrituras de identidad.** Inventariar instancias y tareas que escriben `hotel_users`, aceptan invitaciones, crean hoteles o gestionan usuarios: Dashboard `/api/settings/users`, `/api/platform/users`, `/api/platform/hotels`, creación/selección de espacios, resolución de invitaciones al iniciar sesión, scripts administrativos y cualquier integración detectada en el inventario privado. Bloquear temporalmente esas escrituras y drenar solicitudes en curso, incluidas las disparadas durante lecturas de contexto. Verificar cero escritores antiguos mediante instancias/rutas activas, logs y transacciones de base; registrar hora y versiones. Si no se puede aislar escritura de lecturas, usar mantenimiento temporal de acceso antes que permitir escritores concurrentes. Dashboard/Inbox de sesiones existentes pueden conservar lectura si el drenaje lo permite. No tocar envíos, conexiones ni permisos para conseguirlo.
5. **SQL primero.** Aplicar únicamente `supabase/sql/add_organizations.sql` en una transacción, después de los gates anteriores y antes del código nuevo. No hay otra migración de organizaciones en esta entrega ni carga automática de clientes. Comprobar commit de transacción y repetir el preflight READ ONLY. Verificar nuevas tablas/FK/índices parciales, funciones y triggers; ningún hotel existente debe haber adquirido organización y ningún UUID/rol previo debe cambiar. Si el lock_timeout aborta, conserva el estado previo: revisar bloqueo antes de reintentar, sin aumentar el alcance.
6. **Publicar el SHA nuevo con gestión pausada.** Desplegar Dashboard y todos los consumidores que resuelven/escriben asignaciones. No incorporar hoteles, crear membresías ni concesiones derivadas mientras quede una instancia antigua. El SQL permite hoteles sin organización y filas independientes, pero sustituye unicidades y guardas; no se presume que un escritor antiguo sea compatible. Confirmar SHA/imagen y retirada de réplicas, previews/rutas accesibles y tareas antiguas en el inventario. Mantener la pausa si falta alguna evidencia.
7. **Contrato posterior antes de incorporar.** Verificar lectura PostgREST de campos nuevos, ausencia de errores de caché de esquema y resolución autenticada de contexto. Comprobar metadatos/privilegios: `anon` y `authenticated` sin acceso directo a tablas de organizaciones ni RPC de mutación/aceptación; `service_role` con SELECT de organizaciones y EXECUTE de las RPC aprobadas. Helpers de ámbito invocables por `authenticated`/`service_role`, con funciones internas privadas; políticas restrictivas en hoteles, identidades y tablas operativas. Verificar una apertura interna auditada con el UUID real del actor. No probar mutaciones privilegiadas sobre registros reales como ensayo: estas negativas ya se prueban en PostgreSQL desechable. Confirmar comportamiento real Auth/PostgREST/Realtime usando las sesiones de prueba autorizadas, sin enviar ni reclamar mensajes.

El contrato crea membresías ordinarias de las asignaciones independientes conservadas y aborta ante una membresía incompatible; no la reactiva ni promociona a administrador. Comparar antes/después con el mapa; repetir solo acciones idempotentes del contrato. Comprobar separación entre organizaciones, independiente y roles diferentes por hotel con sesiones autorizadas. No incorporar la demo por omisión ni copiar ejemplos del laboratorio.
9. **Restablecer gestión y observar.** Solo con todos los consumidores nuevos y comprobaciones correctas, levantar las pausas registradas. Validar entrada, directorio, cambio de hotel, Inbox, equipo y retorno; comprobar errores 401/403/404 y auditoría. Mantener flags, proveedores y configuración anteriores. Documentar versiones activas, procesos restablecidos y cualquier limitación de sesión.

### Hoteles y usuarios pendientes

Los hoteles `organization_id IS NULL` siguen disponibles por asignaciones independientes activas y vinculadas; no se crea una organización ficticia. Los usuarios sin membresía no reciben alcance de cadena; los no asignados siguen sin acceso. Invitaciones no aceptadas solo se vinculan a una identidad Auth verificada mediante el contrato. Una asignación activa sin UUID exige reconciliación aprobada antes de migrar; no se desactiva para salvar el gate. Incorporar un hotel conserva los roles independientes y añade membresía ordinaria. Un conflicto con membresía revocada requiere decisión explícita; no autoriza recuperación automática. Transferencias entre organizaciones no están soportadas en esta primera versión.

### Recuperación

- Si la transacción SQL falla, no publicar código dependiente; conservar evidencia y comprobar rollback. No ejecutar fragmentos sueltos para sortear el fallo.
- Con SQL confirmado y antes de incorporar: mantener pausadas escrituras incompatibles, corregir hacia delante y conservar UUID/accesos. Un retorno de código solo podría evaluarse después de demostrar ausencia de membresías/concesiones y compatibilidad con nuevas unicidades/RLS; no se ofrece como opción segura automática.
- Después de incorporar: no volver a consumidores que ignoren membresías, origen de concesión o revocaciones. Mantener código/contrato nuevos y pausar gestión afectada; recuperar hacia delante. Conservar asignaciones, auditoría y respaldo. No borrar concesiones para reconstruir índices viejos, no reactivar accesos revocados ni restaurar un backup sobre actividad posterior sin reconciliarla.
- Registrar cada pausa y restaurar únicamente consumidores acreditados con el contrato nuevo. Nunca activar automatizaciones ni reencolar intentos de envío durante esta transición.
